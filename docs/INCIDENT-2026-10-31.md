# Incident 2026-10-31 — a published Session event made a session unreadable

## Symptom

After restarting DeepSeek Harness, one existing conversation refused to open:

```
failed to observe session "session-3c7eb632-c891-45c2-9642-10d83e2756f4":
session "..." contains event type "project-beta/state" (seq 3339) unknown to this
harness and not marked ignorable; refusing to interpret the log
```

The session ran fine before the restart. Nothing in the transcript hinted at a problem,
because the failure happens only when the log is read back.

## Root cause

`src/index.ts` published a project snapshot into the session's event stream:

```ts
sessions.get(sessionId)?.append(PROJECT_STATE_EVENT, { snapshot });
```

`PROJECT_STATE_EVENT` is `'project-beta/state'` — a type declared by this repository, not by
the Host.

The Host validates stored event types in one place, `validateStoredEvents` in
`@deepseek-ai/dsh-session-persistence/storage-contract`:

```ts
if (!KNOWN_SESSION_EVENT_TYPES.has(event.type) && event.ignorable !== true) throw unsupported(...)
```

`KNOWN_SESSION_EVENT_TYPES` is generated from the Host repository's own `SessionEventMap`
(`scripts/gen-persistence-catalog.ts`). Its source comment states the boundary explicitly:

> Downstream (out-of-repo) plugin events are outside this list by construction. The persisted
> `SessionEvent.ignorable` marker is the compatibility mechanism; event-name registration was
> rejected because it does not classify omission safety and would make reads
> composition-dependent.

So a plugin event type can never be admitted by registering a projection, which is what the
removed comment in `src/index.ts` had assumed. Two consequences matter here:

- **Write does not validate; read does.** Appending succeeded at runtime and only surfaced as
  a broken session on the next load.
- **The only supported escape hatch is an `ignorable: true` envelope**, and live
  `Session.append()` cannot set it — it accepts `{sourceEventSeqs, surfaceOp}` only.
  `appendPluginRecord()` can write ignorable `plugin:` records, but the Host reserves it for
  its own experimental packages, and a session format migration keeps those only on a
  best-effort basis.

The Host's own guidance, from its architecture notes:

> Derive state from existing events, or keep plugin-owned data in a storage service found
> through inspection.

## Blast radius

- Two events in one session: `seq 3339` (revision 4) and `seq 3519` (revision 6).
- Of 125 session directories on this machine, only that one contained
  `"type":"project-beta/state"`.
- The session log cannot be repaired by deleting the events: the reader also enforces
  continuous `seq` (`expected N, got M`), so removal shifts every later event.

## What was done

1. **Stopped the write.** The `sessionProjections` / `sessions` injection and its publisher
   were removed from `src/index.ts`. `runtime.setPublisher` now has no caller, so
   `ProjectEngine.publishState` returns immediately.
2. **Repaired the log.** The session was decompressed, `"ignorable":true` was inserted into
   the envelope of the two affected events (nothing else changed — `diff` showed exactly two
   lines), and it was recompressed. Verified afterwards that all 3521 events still parse, that
   `seq` remains continuous `0..3519`, and that Node's native `zlib.zstdDecompressSync` reads
   the new frame.
3. Original backed up at
   `C:\Users\Administrator\.dsh\session-backups\session-3c7eb632-....bak-20261031-0920`
   (sha256 `8261253125922ee8a26b175a8459aaf8059216a455d108517c57073f382dc2d2`).

## Closed (2026-10-31, `4ab20ec`)

The whole chain is gone: `src/core/projectState.ts`, `src/host/projections.ts` and their unit
tests, `setStatePublisher` / `publishState` and its five call sites, the `publisher` option,
`HostSession.append`, the three projection types, and the `zod` dependency that existed only
for the projection schema. `test/unit/no-foreign-session-events.test.ts` now fails the build
if `src/` mentions `project-beta/` or calls `.append(`.

Blast-radius sweep (2026-10-31, after the fixed build had been running for over an hour):
179 stored session logs decoded frame by frame on this machine — exactly **one** contains
`project-beta/state`, with **2** events, both marked `ignorable:true`; **zero** unmarked, and
no log failed to decode. No projection is registered any more and this repository still has no
client bundle, so the next attempt must render in a client bundle and read state from a file or
a Host storage service — not from the session event stream.

## Follow-up: the rescue silently hid the session (same day)

Adding `"ignorable":true` made the log pass `validateStoredEvents`, but the session then
vanished from the desktop session list instead of reappearing. Root cause was **physical, not
logical**: the rescue re-compressed the whole log with the `zstd` CLI into a single frame.

The Host never decompresses a log to read its header. `readFirstZstdLine` locates the first
frame, decompresses only that frame, and asserts it is exactly one header line:

```js
function assertZstdHeaderFrame(plaintext) {
  if (plaintext.length === 0 || plaintext.indexOf(10) !== plaintext.length - 1)
    throw new Error("corrupt Zstandard session log: first frame is not exactly one header line");
}
```

A single-frame log makes frame #1 the entire 14 MB body, so the assertion throws, the reader
records `SessionPersistenceCorruptionError`, and `listArtifacts` drops the session with
`if (metadata === void 0) continue;` — no error surfaces anywhere, in the UI or in the logs.
The writer's real layout is `encodeMaterialization`:
`Buffer.concat([compressZstdFrame(header + "\n"), compressZstdFrame(body + "\n")])`, i.e.
**header in its own frame, event body in a second frame**, both compressed with
`{ params: { [ZSTD_c_checksumFlag]: 1 } }`.

Fix: re-encoded as two frames (177 B header frame + 1,969,411 B body frame). Verified that a
magic-number frame scan finds exactly two boundaries at offsets `0` and `177`, that the first
frame satisfies `assertZstdHeaderFrame`, and that `validateStoredEvents` still passes with 3520
events.

Lesson for any future surgery on a stored log: **never re-compress a session artifact as one
stream.** Preserve or rebuild the frame boundaries, or the Host will treat the file as corrupt
while every content-level check still passes.

## Lesson

A Session event is a Host-owned, persisted, schema-validated artifact. Publishing into it is
not an ordinary sink — it is a claim that the type belongs to the Host's catalog. Extensions
do not get to make that claim.
